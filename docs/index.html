A terminal coding agent in C for a model running on your Mac.

Tested with Qwen3.8-27B served locally by Splash with a DFlash2 drafter. No cloud account, no API key. The commands the model runs are sandboxed on macOS.

How the loop works

Local models fail in repetitive ways: malformed tool calls, repeated commands, stalls. flywheel handles some of them around the model.

Loop breaker

When similar commands keep returning similar results, prunes those turns, adds a correction and raises temperature.

Strict tool calls

Recovers shell commands from JSON with raw control characters. Truncated arguments are rejected, never run.

Structured edits

write_file and edit_file with unique-match replacement, confined to the project.

Verification gate

A type check or compile per language, then one requirement-by-requirement pass. The interactive UI asks before running the check.

Live terminal UI

Type while it works, Esc to interrupt, collapsible output, streaming markdown, end-to-end tokens per second. /copy copies the last reply.

Images

Drag a file in, type its path or an image URL, or /paste from the clipboard. Naming a file attaches it, even outside the project. The engine must serve the model with vision.

Sandbox on macOS

Model commands and checks cannot write outside the project and a private temp directory, or reach the network unless you approve it. Limits apply.

Small

About 11k lines of C, plus vendored cJSON. libcurl only on macOS; the Linux build is static and speaks plain HTTP.

The stack as tested

  • Model: uub336/Qwen3.8-27B-pi-mlx-4bit (about 15 GB, MLX)
  • Drafter: z-lab/Qwen3.8-27B-DFlash2 (about 3.9 GB)
  • Engine: Splash 1.7.2, brew install incoai/tap/splash
  • Machine: Apple M5 Max, 64 GB. Smaller Macs are untested.

Get started

macOS on Apple Silicon, with clang and libcurl. About 19 GB of downloads; setup needs Homebrew and aria2c (brew install aria2) installed first. Server already running? Set FW_ENDPOINT.

git clone https://github.com/megasoft1978/flywheel
cd flywheel && make

./flywheel setup   # optional: engine + model, asks first
./flywheel init    # per-project instructions
./flywheel         # interactive session

Safety, stated plainly

flywheel runs shell commands on your machine. Here is what it does and does not protect against.

  • Sandbox on macOS. Commands the model runs, the verification gate and benchmark grading scripts run under sandbox-exec. They cannot write outside the project and a private temp directory (grading scripts have their own). In a linked git worktree they can also write parts of the main repository’s git data. They have no network unless you approve it for one command, which can then reach any address. Run an untrusted repository or task in a VM.
  • Reads are limited under your home directory to the project, toolchains, downloaded dependencies and some git files; a fixed list of credential stores stays closed, but other secrets in those places, such as a project .env, are readable. Everything readable outside your home stays readable and can reach the model. Started in your home directory itself, commands can read and write nearly all of it, except those stores and a few read-only files. Start it in a project directory.
  • What it does not cover. Files inside the project can be changed, including build scripts you may later run outside the sandbox. File tools use their own project confinement. Background processes of commands without network can keep running.
  • The interactive UI asks before anything outside a short read-only list, including git, and before the verification gate. Commands you mark “always allow” are not asked again, even if the model has since changed the files they run. One-shot and bench modes approve everything automatically (network excepted).
  • No sandbox on Linux yet. The interactive UI still runs there: approved commands can write anywhere you can and use the network. Without a sandbox, one-shot and bench refuse to run unless you pass --unsafe, which turns the sandbox and environment filtering off.
  • Some tools stop working inside the sandbox, for example global installs, git config, rebase and Docker. The full list is in the README.

Limits

  • Images go only from what you type or paste, in the interactive UI and one-shot mode; no audio or video.
  • No API key support. The Linux build has no HTTPS and no sandbox.
  • No context compaction.
  • Go and Rust checks are experimental.
  • Tuned on the private suite above.
  • No Terminal-Bench 2.1 results yet, and no comparison with other agents on the same model (planned protocol).
